The backup destination changed from Google Cloud Storage to Wasabi (S3‑compatible object storage). This resolved Gate 21 rather than complicating it: Wasabi has no Workload Identity concept and no GKE‑specific credential path to route around — every producer authenticates with a plain scoped access‑key/secret‑key pair, the same mechanism regardless of where it runs. Retained for provenance only: the destination moved again on 14 September 2026, from Wasabi to Backblaze B2, per the amendment below. Where this paragraph and that amendment disagree, the amendment governs.
Amended 14 September 2026 — backup destination moved from Wasabi to Backblaze B2
The backup and recovery destination is now Backblaze B2, reached through its S3‑compatible API. Gates 17, 18, 19, 20, 21, 25, 26, 30 and 31 are rewritten below in B2's terms. Gates 22–24 and 27–29 remain backup‑destination‑agnostic and are unchanged. This is not a rename: four differences between Wasabi and B2 change what those gates actually require, and each is reflected below rather than carried over.

B2 uses capability‑scoped application keys, not AWS‑IAM‑compatible policy JSON. B2's S3‑compatible API does not support IAM roles, bucket policies, object ACLs or STS. Gates 20 and 21 are rewritten around the application‑key model (a master application key as the root‑equivalent, and restricted keys carrying an explicit capability set, an optional bucket restriction and an optional name prefix).
B2 application keys can carry a native expiry (validDurationSeconds, under 1000 days). Gate 21's rotation requirement is therefore enforceable by the credential itself, not only by process.
B2 Object Lock can be enabled on an existing bucket, including as a one‑time b2_update_bucket operation — it is not create‑time‑only. Gate 19's "recreate, do not convert" requirement was a Wasabi/S3 constraint and is withdrawn; the two‑phase Governance‑then‑Compliance sequence is kept, because that protects against locking the wrong retention period, which is still irreversible.
B2 charges per byte‑hour with no minimum storage duration, so Wasabi's 90‑day minimum‑duration penalty on hourly‑churning buckets (etcd snapshots, WAL) does not apply and that cost warning is withdrawn. It is replaced by a different one: B2 egress is free only up to 3× average monthly storage, and a full restore is exactly a large egress burst in a short window (Gates 18, 24, 29).
Amended 13 September 2026 — gap closure: network policy and namespace articulation
Four gaps found in review of this document's network‑policy and identity content and of Gate 29 — unresolved namespace naming, the Wave 5/Wave 6 NATS‑Temporal overlap, thin per‑namespace Kubernetes RBAC, and an undeclared tenant‑to‑namespace model — are closed by new Gates 32–35 (Part D). This is still Revision 3; the amendment adds gates and cross‑references only and changes no decision already recorded for Gates 0–31. Source: docs/Engineering Documents/Gap Closure Plan — Network Policy.txt, whose four phases this amendment incorporates. That source document is superseded by this amendment and is retained only for provenance. Gates 32–35 follow this plan's own convention of not pre‑assigning deliverable (D) or exit‑gate (EG) numbers in gate text — the gate ledger (docs/evidence/gate-ledger.md) assigns those cumulatively, only when a gate reaches PASS, continuing from its recorded position at that time.

Highest‑priority unresolved issue
Proving each producer's actual path to Backblaze B2 against its exact pinned version. B2 exposes a first‑party S3‑compatible API, not a cross‑cloud interoperability workaround, so the protocol risk that existed under GCS mostly disappears — CloudNativePG, Longhorn and k3s etcd all have native, documented S3‑compatible backup‑target support, and B2 accepts both path‑style and virtual‑hosted addressing, which removes the specific addressing mismatch that bites some S3‑compatible backends. What is not yet proven is B2‑specific behavior under this exact stack: multipart limits, request‑rate and throttling behavior during a full restore, and whether a full restore's egress exceeds the free allowance (3× average monthly storage) and at what cost. B2's S3‑compatible API also does not implement object ACLs, IAM roles, bucket policies or object tagging — any producer or tool that assumes those must be identified before it is trusted. See Gate 17.

Non‑negotiable architecture policies
No Hetzner endpoint, account, bucket, load balancer, DNS zone, secret, Terraform state, backup, recovery artifact, or CI variable may be required by production or disaster recovery.
The backup and recovery destination is Backblaze B2 (via its S3‑compatible API), provisioned as a separate infrastructure‑as‑code stack outside the netcup cluster, with deletion protection on every locked bucket (Gate 31).
All versions and deployment artifacts are pinned. OCI Helm charts should be pinned by digest where supported.
A healthy rerun must report changed equals zero for host and bootstrap automation and must not restart k3s, Cilium, CoreDNS, kube‑vip, or storage services.
No workflow may hand‑patch a GitOps‑owned object. Emergency changes require an incident record and immediate reconciliation into Git.
MinIO is one distributed deployment of exactly four server pods, never described as "four replicas" or four independent instances. Each pod requires a distinct node, storage device or dedicated filesystem path, and topology label (Gate 23).
Longhorn may protect ordinary PVC workloads, but MinIO data volumes use direct local storage so MinIO erasure coding remains the sole replication layer.
Default deny is never applied to an application namespace until observed dependencies are expressed as reviewed policies and both allowed and denied paths are tested.
Backup credentials are separate from runtime credentials. Production workloads cannot delete immutable backup generations. No backup writer identity can delete a bucket or modify its retention policy (Gate 20).

GATE 17

B2 has no storage‑class tiering — it is flat‑rate hot storage, which simplifies the "storage class" decision GCS required — and it bills per byte‑hour with no minimum storage duration, so Wasabi's 90‑day early‑deletion penalty does not apply here. veridex-etcd-backup (hourly snapshots, 48 kept) and veridex-cnpg-backup (WAL) churn constantly and are therefore cheap to prune aggressively on B2; prune on schedule rather than buying a longer retention window to dodge a minimum‑duration charge that does not exist.

The cost risk moves to egress instead. B2 includes free egress up to 3× average monthly storage, then charges per GB beyond it. Routine operation stays far inside that allowance because backups are write‑mostly; a full restore is the opposite — it downloads most of what is stored, in a short window, potentially across several buckets at once. Estimate the egress of a complete Gate 29 drill against the 3× allowance, record what it would cost if it exceeds it, and state whether a drill is rate‑limited or staged to stay inside the allowance. A restore that is financially discouraged is a restore that does not get practised. Also record which B2 API call classes each producer generates, since transaction pricing differs by class and a chatty backup client can cost more than the bytes it stores.

GATE 19
Object Lock (Compliance mode) activation
Backblaze B2 implements Object Lock in two modes. Governance‑mode retention can be modified or overridden by a client whose application key carries the capability to do so. Compliance‑mode retention cannot be removed by any user — its date can be extended, never shortened — so committing to a Compliance period is irreversible in the only direction that matters.

Unlike Wasabi and S3, B2 does not require Object Lock at bucket creation: it can be enabled when the bucket is created, on an existing bucket, or as a one‑time b2_update_bucket operation. The previous revision's "recreate the bucket, do not convert it" requirement was a Wasabi constraint and is withdrawn. The two‑phase activation below is kept anyway, and for a different reason: it protects against locking in the wrong retention period, which no provider can undo.

Enable Object Lock on the bucket (versioning is required and turns on with it) with either no default retention or a
Governance‑mode
default retention only.
Run upload, restore, denial and lifecycle tests.
Obtain documented approval of the retention period.
Set the default retention mode to
Compliance
with the approved period.
Verify the policy cannot be reduced, removed, or bypassed — including by the master application key.
Store the lock evidence.
Decide separately between bucket‑level default retention, per‑object retention overrides, Legal Hold flags (indefinite, no expiry, independent of the retention period), and file versioning — they solve different problems and are not interchangeable.

Stop condition
A bucket locked before step 2 or 3 is complete; a Compliance period set without recorded approval; or a retention mechanism chosen without recording which problem it solves.

Reference: Backblaze B2 — Object Lock documentation

GATE 20
Backblaze B2 account and access isolation
A different provider than Hetzner is not sufficient protection if one compromised administrator can delete the cluster and its backups. B2's master application key is the root‑equivalent — it carries every capability, reaches every bucket, has no prefix restriction and no expiry — so the same root‑key risk applies directly, under a different name. Required:

A dedicated B2 account separate from any account used for other workloads, with separate billing and recovery contacts.
MFA on console login for privileged human identities; no routine use of the master application key by any automation.
Every identity is a restricted application key carrying an explicit capability set, scoped to one bucket (and a name prefix where it helps) — B2 has no IAM policy documents, no IAM roles, no bucket policies and no STS, so the capability list on the key IS the policy and must be enumerated and reviewed as one.
Backup writers hold writeFiles but not deleteFiles, and hold no bucket‑management capability that would let them delete a bucket or alter its Object Lock or retention configuration.
Restore identities hold readFiles only, and are unused except during drills.
Bucket and access logging exported to an independently protected destination outside the B2 account.
Recovery access proven without the production cluster.
Alerts for application‑key creation, lifecycle, retention and bucket configuration changes.
Stop condition
Any human or workload identity holding both write and delete/retention‑modification capability on a locked bucket, or any automation using the account's master application key.

Reference: Backblaze B2 — Application Keys documentation

GATE 21
Backblaze B2 application‑key scoping and lifecycle
The credential question this gate existed to answer under GCS — how does a non‑GKE k3s cluster authenticate without Workload Identity Federation — is moot under B2: there is no federation concept, GKE or otherwise. Every producer authenticates with an application key id and secret, presented to the S3‑compatible API as an access‑key/secret‑key pair, the same mechanism regardless of where the workload runs. What remains is disciplined key handling, not protocol selection:

Every producer authenticates with its own restricted application key — never the master application key.
One key per producer/bucket pairing, restricted to that bucket (and a name prefix where the producer writes under one), so a compromised key exposes only its own bucket.
Each key's capability set is the minimum that producer actually needs, and is recorded alongside the key in the secret register. A writer that never prunes does not get deleteFiles.
Keys are encrypted through SOPS in Git and never committed in plaintext — the same class of failure as the MINIO_KMS_SECRET_KEY incident in Gate 22, and this gate exists so it does not recur for B2 keys.
Keys are rotated on a defined schedule and immediately on suspected exposure. B2 application keys accept a native expiry (validDurationSeconds, under 1000 days) — set it, so an un‑rotated key fails closed on its own rather than living until someone notices.
CloudNativePG is configured with plain s3Credentials and an explicit endpointURL pointed at the B2 region endpoint — never a googleCredentials block, which does not apply to a non‑Google endpoint.
Stop condition
Any automated workload using the master application key, any key without a bucket restriction, or any application key committed in plaintext anywhere in the tree.

Reference: Backblaze B2 — Application Keys documentation

GATE 24
MinIO capacity policy
Actual thresholds, not a general safety margin. For four 30 GiB drives: raw capacity 120 GiB; approximate erasure‑coded usable capacity 60 GiB; operationally safe usable capacity is less than 60 GiB, because healing requires headroom. Define:

Warning threshold · Critical threshold · Write‑stop/escalation threshold.
Minimum free capacity during one‑node loss · Maximum supported object count.
Healing‑time objective · Expansion procedure.
What happens when differently sized disks are used.
Monitoring for offline drives, healing backlog and write quorum.
GATE 25
MinIO backup semantics
"Mirror to B2" needs a precise policy — a plain mc mirror --remove would be dangerous for an immutable backup, since it can propagate malicious or accidental deletion. Because B2 exposes an S3‑compatible API, MinIO's native server‑side bucket replication can target it directly; prefer that over a client‑side mirror script where available, since it handles versioning and delete markers more faithfully. Confirm against the pinned MinIO release that its replication path works against B2 specifically, given that B2's API omits object tagging and ACLs, which some replication implementations set as a matter of course. Answer explicitly:

Are all object versions preserved? Are delete markers copied?
Are legal holds and retention metadata preserved or reconstructed?
Are bucket policies, users, groups and service accounts backed up? Are lifecycle rules backed up?
Is server‑side encryption metadata recoverable?
Does deleting from MinIO propagate deletion to B2?
Is replication continuous or scheduled? What is the maximum replication lag?
How are failed objects retried? How is completeness reconciled?
Stop condition
Any replication tool run with delete propagation enabled against a bucket meant to be immutable.

Four‑instance MinIO policy
Placement fundamentals below; enforceable scheduling rules are Gate 23, capacity thresholds are Gate 24, and backup semantics are Gate 25.

Placement and storage
Label the four selected nodes with stable failure‑domain labels and use required pod anti‑affinity or topology spread so the scheduler cannot co‑locate instances.

Defined network policy rollout
Policy enforcement is a promotion process, not a bulk manifest deployment. Every namespace moves independently through the following states, namespace by namespace. A namespace cannot advance while its prior state lacks evidence.

State	Action	Promotion gate	Rollback
P0 Inventory	Record workloads, ports, service accounts, DNS, API, ingress, metrics, storage, backup and external dependencies.	Owner approves dependency map; no unknown critical flow.	No enforcement exists.
P1 Observe	Use Hubble and application traces across normal operation, batch jobs, backups, failover and maintenance.	Observation covers an agreed representative window and exceptional workflows.	Extend observation.
P2 Declare	Commit default‑deny plus explicit ingress and egress allows, but do not enable enforcement for the namespace yet.	Peer review confirms selectors, ports, protocols and namespaces; manifests pass policy lint.	Revert Git change.
P3 Canary	Enforce on a canary workload or non‑production namespace with equivalent service accounts and dependencies.	Positive tests pass and prohibited paths fail. No unexplained drops.	Revert policy commit; Argo sync; capture dropped flows.
P4 Enforce	Enable policy for one production namespace during a controlled window.	Readiness, transactions, metrics, logs, backups and cross‑service flows remain healthy for the soak period.	Revert the exact policy commit through GitOps; do not hand‑delete except break‑glass.
P5 Prove	Run automated allow and deny tests and retain evidence.	All expected allows succeed; all forbidden flows fail; alerts are clean.	Return to P3 or P2.
P6 Maintain	Detect service, label, port and policy drift in CI and scheduled tests.	Every workload change includes policy impact; periodic negative tests pass.	Block release or roll back the workload change.
Baseline policy requirements
Default deny ingress and egress for application namespaces. kube‑system and other control namespaces require component‑specific policy and must not receive a generic blanket policy.
Permit DNS only to the declared CoreDNS Service or endpoints over required UDP and TCP ports. Do not allow arbitrary port 53 destinations.
Permit Kubernetes API access only for service accounts that demonstrably require it and only to the API destination and port.
Express ingress‑controller to backend flows explicitly by namespace and workload selectors.
Express Prometheus scraping and log shipping explicitly. Monitoring must not become a broad namespace‑to‑namespace allow.
Declare CNPG replication, operator, backup and object‑store egress; NATS routes and clients; Temporal frontend, matching, history, worker and database paths; MinIO client and administrative paths.
External egress uses approved destinations where technically stable. DNS‑based policy requires an explicit Cilium FQDN policy design and failure testing.
Backblaze B2 egress — DNS, HTTPS to the B2 regional S3 endpoint, FQDN policy and TTL handling, certificate validation, and denial of arbitrary external storage destinations — is declared per namespace under the same promotion sequence, never as a bulk exception (Gate 30).
Every policy bundle includes tests for intended access and at least one denied same‑namespace, cross‑namespace and external destination.
Emergency rollback is a Git revert with Argo reconciliation. Break‑glass deletion is audited and followed immediately by a Git correction.
