--- disclosed incident: the first (invalid) test attempt ---

The first attempt at this exact test used the same token but reused a
stored argocd CLI login context (`~/.config/argocd/config`, current-context
"kubernetes", core: true) left over from an earlier, unrelated diagnostic
`argocd login veridex-cluster --core` call made during this same gate's
build. That stored context's `core: true` setting silently overrode the
`--server`/`--auth-token` flags on the `app sync`/`app delete` commands --
confirmed by the tool's own "URL" field printing a random ephemeral local
port each invocation, the signature of --core mode's internal proxy, rather
than the fixed `localhost:18443` explicitly requested.

Because --core mode talks directly to Kubernetes using the ambient
kubeconfig (root's own k3s admin kubeconfig, i.e. cluster-admin) instead of
Argo CD's own RBAC-enforcing API, both commands succeeded -- the tool
reported "application 'root' deleted" -- silently bypassing the very RBAC
policy under test. This deleted the live `root` Application object in
production. Blast radius: confined to that one object. At the time of the
incident, `main` did not yet contain this gate's real `gitops/` content
(only .gitkeep placeholders), and `gitops/bootstrap/**` is excluded from
the root app's own recursive scan, so nothing was cascade-deleted -- verified
immediately after by listing every object in the `argocd` namespace
(Deployments/Services/Pods/the `veridex` AppProject all present and
untouched) and every cluster namespace (unchanged). Remediated within
minutes by re-applying the still-present rendered manifest
(`kubectl apply -f /tmp/root-application.yaml`) -- `application.argoproj.io/root
created`, confirmed Synced/Healthy immediately after.

Root cause fix for the retest: deleted the stale `~/.config/argocd/config`
entirely and used an isolated, explicit `--config <temp path>` with
`--core=false` for every command in the corrected run above, so no stored
context could silently substitute cluster-admin access for the token under
test. This was a testing-harness bug (leftover local CLI state), not an
AppProject/RBAC policy defect -- the corrected run above shows the policy
enforcing correctly once the test itself was honest.
