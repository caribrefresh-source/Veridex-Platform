EG102 -- would any legitimate flow be dropped?          PASS
--------------------------------------------------------------
Method: hubble observe --verdict AUDIT, filtered POSITIVELY to flows whose
source or destination carries reserved:host. Stage D policies select host
endpoints only, so every verdict they can produce is in that set.

Result over a 45-minute window: 31 host-ingress audit verdicts, ZERO of them
legitimate traffic. All were reserved:world probing closed ports.

THREE CRITERIA WERE TRIED. The first two were WRONG and are recorded so the
conclusion cannot be misread:

  (a) "any host-scoped audit is a failure"          -> reported 36 failures
      Rejected: counts internet background scanning, which the policy is
      SUPPOSED to drop.

  (b) "any audit against a protected port"          -> reported 1 failure, twice
      Rejected: counts world -> 9100 and world -> 6443 scans. Those ports are
      protected FROM the internet and reachable only from the vLAN or pod

      A failure requires either an internal source (10.2.0.0/16, 10.44.0.0/16,
      10.45.0.0/16, or a cluster/remote-node/health/kube-apiserver identity)
      hitting an internal port, or reserved:world hitting a deliberately
      public port (22, 80, 443, 32537, 32538). Neither occurred.

EG104 -- rollback drill                                 PASS, with a finding
--------------------------------------------------------------
Method: delete both CCNPs while audit mode held, observe, allow Argo CD
selfHeal to restore them.

  03:41:05Z  kubectl delete -- both objects reported deleted
  03:41:07Z  veridex-host-baseline recreated by selfHeal        (+2s)
  03:41:13Z  veridex-host-public-ingress recreated by selfHeal  (+8s)
  03:42:42Z  post-state: 2 CCNPs, 5/5 audit=Enabled (Audit),
             0 restarts, 9/9 apps, all probes 200

FINDING 1 -- the escape hatch does not work the obvious way. A bare
kubectl delete was undone in TWO SECONDS. The warning in the policy header is
now VERIFIED rather than asserted: in a real lockout, deleting the CCNPs buys
seconds, not a fix. The Git commit must be reverted as well or selfHeal closes
the hatch while the operator is still working.

FINDING 2 -- the rollback has its own transient failure window. NEW, and not
anticipated by the procedure. During the recreate, legitimate VXLAN
(UDP/8472 from 10.2.1.11, veridex-server-2) was audited as a would-be drop:
the host endpoint had policy ACTIVE but its rules NOT YET COMPUTED. Confirmed
transient -- zero internal-source audits before the delete, zero within 90
seconds after.

  In audit mode this cost nothing.
  UNDER ENFORCEMENT it would have been a brief cross-node network partition,
  because VXLAN carries all inter-node pod traffic.

Consequence for Stage E: reverting under enforcement is not instantly safe. It
has its own few-second outage. The safer emergency order is to disable
enforcement FIRST (return the host endpoints to audit mode), and only then
revert Git -- rather than reverting and hoping. This should be decided before
Stage E, not discovered during an incident.

LIMITATIONS -- what this evidence does NOT establish
----------------------------------------------------
1. NO ANSIBLE RUN occurred inside the window. The procedure requires one so
   node-to-node and control-plane flows are exercised deliberately rather than
   waited for. EG102 therefore passes on ORGANIC TRAFFIC ONLY. Ansible-driven
   flows are untested. Neither party in the session had SSH access to the
   nodes (10.2.1.10:22 unreachable from the operator workstation; no private
   keys present), so this is an access limitation, not an oversight.

2. THE COLD-APPLY PATH IS UNMEASURED. EG104 exercised delete-then-recreate.
   Stage E actual sequence is a cold apply against endpoints leaving audit
   mode, which may behave differently. Finding 2 above may or may not
   reproduce there.

3. RECOVERY IS NOT CLAIMED. No node loss, no eviction, no real lockout and no
   console recovery was exercised during this window. The console path itself
   was proven separately on 2026-09-18 on one server and one worker only
   (docs/security/incidents/2026-09-18-provider-console-drill.md); three nodes
   remain undrilled.

4. AUDIT MODE REMAINS IMPERATIVE AND UNDOCUMENTED. It is absent from
   cilium-config, is not a cilium-agent argument, and is set by no Ansible
   role. It does not survive a cilium-agent restart. Every one of the results
   above is therefore conditional on a state that no source of truth
   describes, and that CLAUDE.md S15 forbids treating as intended design. This
   should be made declarative or recorded as an expiring emergency mutation
   under S4 before Stage E.
